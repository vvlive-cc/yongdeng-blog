# Agent 的工具调用为什么总失败

做 Agent 最挫败的时刻：prompt 写得很清楚了，模型就是不调对工具，
或者调了但参数瞎填。改 prompt、换模型、加 few-shot……效果时好时坏。

我踩了半年，慢慢发现**大部分问题不在模型，在工具设计**。

下面五种是我遇到最多的，按出现频率排。

## 一、工具描述写成了给人看的

模型判断"该不该调这个工具"完全依赖描述。看看这两种写法：

::: code-group

```python [❌ 常见写法]
{
  "name": "search_docs",
  "description": "搜索文档",
  "parameters": {
    "query": { "type": "string", "description": "查询" }
  }
}
```

```python [✅ 改进写法]
{
  "name": "search_docs",
  "description": (
    "在内部技术文档库中做语义搜索，返回最相关的最多 5 个片段。"
    "适用于查找 API 用法、配置项说明、错误码含义。"
    "不适用于：查找代码实现（用 search_code）、"
    "查询最新新闻（用 web_search）、"
    "计算数值（用 calculator）。"
  ),
  "parameters": {
    "query": {
      "type": "string",
      "description": "自然语言问题，例如 'Kafka consumer 如何设置重试次数'。不要传关键词拼接。"
    },
    "top_k": {
      "type": "integer",
      "description": "返回片段数量，默认 5，范围 1-10。",
      "default": 5
    }
  }
}
```

:::

差别在于三件事：

1. **说清楚什么时候用，更要说清楚什么时候不用** —— 这是减少错误工具选择最有效的手段
2. **参数描述给例子** —— "自然语言问题，例如 xxx" 比 "查询" 有用十倍
3. **明确取值范围和默认值** —— 否则模型会传 `top_k: 100`

## 二、工具太多，且功能重叠

工具超过 10 个以后，选择准确率明显下降。更糟的是有重叠：

```
search_docs      # 搜文档
search_knowledge # 搜知识库
search           # 通用搜索
```

模型面对这三个会怎么选？随机。

**解决办法：**

- 合并重叠的工具，用一个参数区分
- 工具超过 15 个时，做**两阶段选择**：先让模型选"类别"，再在类别内选具体工具
- 用子 Agent 隔离工具集——检索类任务只给它检索工具

## 三、错误信息对模型没有信息量

工具执行失败时，你返回什么给模型？

::: code-group

```python [❌]
return {"error": "failed"}
```

```python [✅]
return {
    "error": "invalid_parameter",
    "message": "参数 date 格式错误。期望格式 YYYY-MM-DD，收到的值是 '2026/11/18'。",
    "hint": "请把斜杠替换为连字符后重试。",
    "received": {"date": "2026/11/18", "user_id": "u123"},
    "expected_schema": {"date": "string, format: YYYY-MM-DD"}
}
```

:::

模型看到第一种只能瞎猜或直接放弃；看到第二种能自己修正并重试。

**错误信息里应该包含：什么错了、期望什么、怎么改、收到的原始值。**

## 四、参数校验太晚

如果工具内部等到执行到一半才发现参数不对，你已经浪费了一轮 token 和几秒延迟。

应该在**工具入口做严格的前置校验**，快速失败：

```python
def execute(name: str, args: dict) -> dict:
    schema = TOOL_SCHEMAS[name]
    errors = validate(args, schema)          # 用 jsonschema 之类的库
    if errors:
        return {
            "error": "schema_validation_failed",
            "message": errors,
            "expected_schema": schema
        }
    try:
        return TOOLS[name](**args)
    except BusinessError as e:
        return {"error": e.code, "message": e.message, "hint": e.hint}
    except Exception as e:
        logger.exception("tool execution failed")
        return {
            "error": "internal_error",
            "message": "工具执行异常，请稍后重试或换一种方式。",
            # 不要把堆栈抛给模型
        }
```

注意最后那个 `except`：**内部异常不要暴露给模型**，否则它会基于堆栈信息编造修复方案。

## 五、上下文被污染

这个最隐蔽。表现是：前面几轮都正常，突然开始乱调工具。

常见原因：

**① 工具返回结果太大**

一个检索工具返回 50KB 的文档片段，塞满了上下文。后面模型"看不见"系统提示了。

对策：工具返回也要做**截断和摘要**，单次返回控制在 2000 token 以内，必要时让模型主动翻页。

**② 错误累积**

连续三次工具失败后，模型会进入"乱试"模式——开始调完全不相关的工具。

对策：连续失败 2 次时注入一条系统消息：

```
你已经连续 2 次调用工具失败。请先说明你理解的任务目标和你认为失败的原因，
再决定下一步。如果确实无法完成，直接告诉用户缺什么信息。
```

**③ 多轮对话没有清理**

历史消息全量带上，几十轮后模型开始"记混"。

对策：对历史做摘要压缩，只保留最近 N 轮原文 + 更早轮次的摘要。

## 排查清单

工具调用出问题时，按这个顺序查：

| 步骤 | 检查什么 |
| --- | --- |
| 1 | 打印完整 prompt，确认模型**真的看到了**工具定义 |
| 2 | 打印模型原始返回，确认是**没调工具**还是**参数错** |
| 3 | 查工具描述：是否说明了"不该用"的场景 |
| 4 | 数工具数量：是否 > 15 个，是否有功能重叠 |
| 5 | 查错误返回：模型能否从错误信息推断如何修正 |
| 6 | 量上下文大小：是否被工具返回塞满 |
| 7 | 看历史轮次：是否有连续失败未打断 |

## 一个实用原则

> **把模型当成一个聪明但完全没有上下文的合作者。**

它不知道你的业务、不知道你们团队的约定、不知道上次为什么失败。
工具定义和错误信息里没写的东西，它就不可能知道。

大部分"模型能力不行"的问题，其实是"我们没把话说清楚"。
