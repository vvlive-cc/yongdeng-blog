# 基于 ShardingSphere-JDBC 的分库双写方案笔记

> 说明：本文是**调研笔记**，重点记录「有哪些路、各自原理与取舍、推荐的组合是什么」。贴近工程落地的配置、时序与伪代码见姊妹篇 [《分库双写落地方案：配置、事务、补偿与灰度》](/posts/java/shard-jdbc-dual-write-design)。

## 〇、动笔前需要你确认的前提

「基于 shard jdbc 实现分库双写」这几个词在不同团队指向不同方案，请先补充以下信息；标注为**高影响**的项会直接决定路径选择。

| # | 待确认项 | 影响哪一部分 | 影响程度 |
| --- | --- | --- | --- |
| 1 | **shard jdbc 具体所指**：是 Apache ShardingSphere-JDBC，还是 Sharding-JDBC 3.x/4.x 老版本、或其它「shard jdbc」类组件 | 能否用内置 Hint/多数据源能力，还是只能走应用层双写 | 高 |
| 2 | 现有架构与规模：单库还是已分库、分片数、表数量、数据量级、读写 QPS | 路由方案、双写性能预算、是否需要异步 | 高 |
| 3 | 双写目标：新老库并行一段时间？灰度切流？还是一次性迁移后下线老库？ | 整体流程与回滚设计 | 高 |
| 4 | 技术栈版本：ShardingSphere-JDBC 版本、MySQL/PG 版本、Spring Boot 版本、ORM（MyBatis/JPA） | 配置样例与 API 可用性 | 中 |
| 5 | 一致性要求：强一致 / 最终一致，可接受延迟，失败补偿方式 | 同步双写 vs 异步双写、幂等与补偿设计 | 高 |
| 6 | 不可变更约束：停机窗口、表结构能否加字段、跨库事务范围 | 校验方案与 rollback 能否落地 | 中 |

## 一、双写要解决的问题与适用边界

### 1.1 它解决什么

双写（dual-write）是**在线迁移 / 在线扩容**过程中的过渡态技术：在同一段时间里，业务写入同时落到「老库（源）」与「新库（目标）」，为切流争取时间窗口，并在切流后保留一条回退通道。

核心要解决三件事：

1. **数据搬迁期间的增量不丢**——全量迁移期间老库仍在写入，这些增量必须也能进新库。
2. **切流可控**——能按比例、按用户/租户把流量逐步导向新库。
3. **可回滚**——发现问题能把流量切回老库，且老库数据仍是最新的。

### 1.2 适用边界

- ✅ 单库 → 分库、分片数扩容、机房/实例迁移、异构迁移（如 MySQL → 新实例）。
- ✅ 对短时不一致可容忍（毫秒~秒级），或有对账兜底的场景。
- ✅ 写 QPS 中等、写逻辑集中在少数服务、事务边界清晰的系统。

### 1.3 不适合的场景（重要）

| 场景 | 为什么不适合 |
| --- | --- |
| 强一致 + 跨库事务不可拆 | 双写无法在单事务内原子提交到两个独立库，必然退化为最终一致 |
| 写路径极度分散（几十个写入点） | 应用层双写侵入面过大，漏写风险高，应优先考虑 binlog 方案 |
| 写 QPS 极高 / P99 敏感 | 同步双写叠加 RT，异步双写放大不一致窗口 |
| 表结构无法添加辅助字段 | 幂等、版本号、对账水位缺少落点 |
| 有「先删后增」等唯一键敏感语义 | 双写两条链路的时序更难对齐，冲突与顺序问题被放大（见下方关联文章） |
| 数据本身不可重放/不可比对（含随机、加密敏感列） | 对账与补偿缺乏依据 |

> 关联：本博客另一篇文章 [《MySQL 唯一索引在并发「先删后增」下的唯一键冲突》](/posts/java/unique-key-delete-insert-conflict) 讨论的唯一键冲突，在双写的两条链路上会被进一步放大——老库与新库各自的并发时序不同，同一条逻辑写入可能在两边触发不同的 1062。选型时务必把唯一约束语义纳入评估。

## 二、可选实现路径对比

四条典型路径，先给结论再展开。

**结论先行**：多数「已用 ShardingSphere-JDBC 且写路径集中」的团队，推荐**路径 A（ShardingSphere 多/影子数据源 + 应用层受控双写）**作为主路径，用**路径 D（binlog 增量 + 对账）**补齐全量搬迁与兜底，二者是**互补**而非二选一。

| 路径 | 原理 | 优点 | 缺点 | 适用条件 |
| --- | --- | --- | --- | --- |
| **A. ShardingSphere 多数据源 / 影子库双写** | 用 ShardingSphere 的路由 + 多数据源能力，把同一逻辑写「影子路由」到老/新两套库；或封装一个 DualWrite 组件在 ORM 拦截层双投 | 复用现成路由、分片规则一套配置；侵入相对可控；可与企业已有分片体系一致 | 双写能力需自己封装（5.x 没有开箱即用的「双写」开关）；跨库原子性仍需业务或框架保证 | 已深度使用 ShardingSphere-JDBC；写路径集中；表结构可加辅助列 |
| **B. 纯应用层双写** | 业务代码显式写两次（或用 AOP 切面拦截 DAO），主库成功即返回，从库异步/同步补写 | 实现直白、可控、与中间件解耦 | 侵入强；写入点分散时易漏写；事务边界要人工保证 | 写入点少、团队愿意改业务代码、需要快速起步 |
| **C. 多数据源 + 分布式事务**（Seata/XA/消息最终一致） | 两个物理库纳入同一分布式事务或消息事务 | 一致性强 | 性能损耗大、运维复杂、对吞吐不友好；XA 常留悬挂/长事务 | 强一致诉求、写量不大、能接受性能代价 |
| **D. binlog 增量同步**（Canal/Flink CDC/Debezium） | 订阅老库 binlog，按库表映射回放到新库 | 对业务**零侵入**；天然覆盖全量迁移期间的增量；可做全量+增量一致性 | 有复制延迟；DDL 与映射要维护；回滚时反向链路要再搭 | 老库是 MySQL 且可开 binlog；写路径分散；需要零侵入 |
| （E. 触发器双写，仅提及） | DB 触发器写影子表 | 零应用侵入 | 触发器性能/维护性差、跨实例难、几乎不用于跨库 | 单实例小表场景，不推荐跨库 |

### 2.1 为什么 A 优于纯 C

跨库强一致（C）在分库双写里代价最高：XA/Seata 会在每次写入上加两阶段开销，且与 ShardingSphere 的本地分片事务混用容易产生「半提交」。实践中更稳的形态是：**一个库内走本地事务，跨库通过「主写 + 异步补偿 + 对账」达成最终一致**——这正是 A 的默认心智模型。

### 2.2 为什么 A 和 D 是互补

- A 负责**切流前的在线写入对齐**与**灰度期间的可控双写**（能按开关只对一部分租户双写）。
- D 负责**历史全量数据一次性搬迁**与**全量对账**，并在 D 的追平能力之上让 A 的异步补偿「追不上时」有兜底（binlog 回放把漏的在老库→新库补齐）。

## 三、推荐路径的关键决策（详见落地方案篇）

推荐组合 = **A 为主 + D 兜底 + 对账中枢**。核心决策点：

1. **写入顺序**：以「老库为权威（System of Record）」先行，还是以「新库为权威」？迁移期通常老库权威、新库跟随；切流后角色对调。顺序决定失败时以谁为准。
2. **同步 vs 异步**：主链路同步写老库（保证业务不被拖慢），新库**同步（短超时）或异步队列**补写；不一致窗口由对账收敛。
3. **事务边界**：双写不放进同一 DB 事务；用「本地事务 + 事务性消息/可靠事件」保证新库写入不丢。
4. **幂等**：新库侧必带幂等键（业务唯一键或 `(shardKey, ver)`），重试与 binlog 回放都不能产生重复副作用。
5. **灰度开关**：以租户/用户维度路由，开关可动态下发；支持「仅双写不读新库」「只读新库」「读老库+读新库比对」多档。
6. **补偿与对账**：定时全量对账 + 实时增量对账，差异入「修复工单」，自动/人工修复后再确认。

## 四、数据校验与切换回滚（方法论）

### 4.1 校验分层

| 层次 | 方法 | 频率 | 目的 |
| --- | --- | --- | --- |
| 实时比对 | 影子读：同请求读老库与新库各一次，比较关键字段 | 灰度期抽样 | 早发现路由/映射错误 |
| 增量对账 | 按业务时间的滑动窗口，两边各取变更集做差集 | 分钟级 | 收敛最终一致的残差 |
| 全量对账 | 分片扫描比对 row count、checksum、抽样明细 | 切换前后各一次 | 切换准入与回滚依据 |

### 4.2 切换步骤（纲）

1. 全量迁移完成 + 增量追平 + 全量对账无差异 →
2. 打开双写（新库同步补写），继续实时对账观察 N 个业务周期 →
3. 灰度读新库（按租户比例），比对读结果 →
4. 全量读新库，老库降为「写仍双写、读不承担」 →
5. 观察稳定后停老库写入（此时老库冻结为快照，保留回滚窗口）→
6. 回滚：任一步异常，把读切回老库、停新库，依据对账差异定向修复。

### 4.3 回滚要点

- 回滚**必须先保数据**：老库在切流后不能立即停写，需保留「回滚窗口」内继续双写或在回滚时用新库差异回填老库。
- 回滚判定要有量化门槛（差异率、错误率、延迟），避免拍脑袋。

## 五、主要风险与监控指标

| 风险 | 说明 | 监控指标 |
| --- | --- | --- |
| 异步双写丢写 | 队列满/异常导致新库缺数 | 双写失败率、待补偿堆积量、追平延迟 |
| 复制延迟 | binlog 链路滞后 | 老库→新库延迟（秒/事务数） |
| 数据漂移 | 两侧字段/精度/时区不一致 | 增量对账差异条数、全量 checksum 差值 |
| 路由错误 | 分片键缺失导致写错库 | 路由命中率、无分片键告警 |
| 性能回退 | 双写叠加 RT | 写 P99、连接池占用、DB CPU |
| 唯一键/时序放大 | 双链路时序不一致 | 1062/死锁计数、失败重试率 |

---

**一句话总结**：双写不是「写两次」这么简单，关键是**定权威、定顺序、定幂等、定对账、定回滚门槛**；ShardingSphere-JDBC 提供路由底座，真正的迁移安全由「双写组件 + binlog 兜底 + 对账中枢」共同保证。
