# 从 Java 后端到 AI 工程：哪些能力能带走，哪些要从头学

转型这件事，网上有两种叙事：一种是"三个月速成年薪百万"，一种是"后端已死赶紧跑"。
都不太真实。这篇写我自己的体感。

## 一、能直接带走的能力

### 工程判断力（最重要）

写 AI 应用和写业务系统，**难的部分是同一件事**：判断什么值得做、什么会出问题。

- 知道一个接口慢 200ms 用户能不能忍
- 知道什么时候该加缓存、什么时候缓存会把问题变得更糟
- 知道"这里加个重试"和"这里必须幂等"的区别
- 知道可观测性不是上线后再补的东西

这些判断在 LLM 应用里同样成立，只是换了一批新的失败模式。

### 分布式系统的直觉

Agent 系统本质上是个**有状态、有外部依赖、可能长时间运行的分布式系统**。

| Java 微服务 | AI Agent 系统 |
| --- | --- |
| 服务超时 | LLM 调用超时 / 流式中断 |
| 重试与幂等 | 工具调用的幂等性（一个退款操作重试两次就完了） |
| 熔断降级 | 模型降级到小模型 / 规则兜底 |
| 链路追踪 | Trace：prompt → 工具 → 模型 → 输出 全链路 |
| 限流 | token 预算与并发控制 |
| 数据一致性 | 多轮对话中的状态一致性 |

真正做过高并发系统的人，看到 LLM 应用的这些问题会觉得**很亲切**——只是参数变了。

### 数据库与检索

RAG 听着玄，本质是**检索 + 拼装**。做过 ES、做过 MySQL 索引优化的人，
对向量检索的召回率、分块策略、元数据过滤会天然有感觉。

### 代码规范与测试

把 AI 输出当不可信输入来对待——这点后端工程师比算法背景的人更有肌肉记忆。

## 二、必须从头学的东西

### 数学直觉（最难）

这是真正的门槛。不是要会推导反向传播，而是要理解：

- 为什么温度调高会让输出发散
- 为什么 embedding 的余弦相似度阈值在不同模型上不能通用
- 为什么 few-shot 里示例的顺序会影响结果
- 为什么同一个 prompt 昨天好用今天不好用

这些没有"标准答案"，**只能靠大量实验积累体感**。后端工程师习惯找确定性的因果链，这里经常找不到。

### 非确定性调试

传统 bug 可复现。LLM 的 bug 可能一百次里出现三次。

必须建立新的调试方法论：

- 把每次调用完整记录（prompt / 参数 / 原始响应 / 耗时 / token 数）
- 建评测集，用数字而不是感觉判断改动好坏
- 接受"线上表现和测试集不一致"是常态

这是我适应得最慢的部分。最初总想"找出那个 bug"，后来才明白要做的是**统计意义上的改进**。

### 快速试错的节奏

Java 后端的习惯是：设计 → 评审 → 编码 → 测试 → 上线，周期以周计。

AI 应用开发的现实是：**一天试五个方案，四个半不管用**。

一开始我很不适应这种"大量无效劳动"的感觉。后来想通了——这不是无效，这是在搜索空间里采样。
关键是**每次实验要留下记录**，否则真的就是白做。

### 前端能力

做 AI 应用绕不开流式输出、打字机效果、Markdown 渲染、文件上传预览。
后端出身的人这块要补，但不用精通——能看懂 Vue/React，会拼组件就行。

## 三、心态变化

::: tip 从"专家"回到"新手"
做了十年 Java，是团队里的"那个人"。转到 AI 领域，突然变成什么都不会的新人。

前半年最难受的不是学不会，而是**效率落差**——以前一天干完的活，现在三天还在试。
:::

::: warning 别把"会调 API"当成"会做 AI 应用"
这是我踩过的坑。会写 `openai.chat.completions.create` 只是起点。

真正难的是：怎么分块、怎么召回、怎么判断答案对不对、怎么在不加成本的前提下提升准确率、
线上出问题怎么定位。这些没有现成答案。
:::

## 四、给同样在转型的人

**不要辞职脱产学习。** 边做边转是唯一稳的路径——用现有工作里的问题当练手素材。

**做一个真实的小项目。** 不是跟着教程复现，而是解决你自己或同事的真实痛点。
我第一个项目是给团队做内部文档问答，上线后天天被吐槽，那半年学到的东西比看多少课都多。

**不要和人比。** 算法背景的同事在数学上强，但他们不一定会做工程。
你的优势是能独立把一个东西做到上线，别丢掉。

**接受慢。** 转型不是三个月的事。我到现在也不敢说"转成了"，只是"在路上"。

## 最后

一个判断标准：当你不再问"我要不要转"，而是开始**具体地烦某个技术问题**的时候，转型其实已经开始了。
